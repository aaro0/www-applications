# Evaluation tooling

| File | Purpose |
|---|---|
| `benchmark.html` / `.js` / `.css` | RQ2 + RQ3 frame-time benchmark, interactive preview for RQ1, static mode for screenshots |
| `tools/compat_screenshots.py` | RQ3 compatibility matrix (Chromium / Firefox / WebKit) and RQ1 comparison screenshots |
| `tools/analyze.py` | Merges exported runs into summary tables and plots |

Everything must be served over HTTP. `feImage` maps do not load from `file://`:

```sh
python3 -m http.server 8000      # then open http://localhost:8000/benchmark.html
```

The deployed page also works: <https://hiskihar.github.io/www-applications/benchmark.html>.

## What the benchmark measures

The filter graphs are generated by `benchmark.js` instead of being copied from `index.html`, so every
configuration and diameter is built the same way. The structure, colour matrices and displacement-scale
formula match the demo, using the circle maps from the demo's image mode.

| Config id | Graph | Primitives | `feDisplacementMap` passes |
|---|---|---|---|
| `none` | no filter (baseline; the loupe and its rim still move) | 0 | 0 |
| `blur` | `feGaussianBlur` | 1 | 0 |
| `disp` | 2 × `feImage`, magnification + refraction | 4 | 2 |
| `blur-disp` | blur + `disp` | 5 | 2 |
| `disp-3/5/7` | 2 × `feImage`, magnification, N × `feColorMatrix`, N refraction passes, (N−1) × `feBlend` | 11 / 17 / 23 | 4 / 6 / 8 |
| `blur-disp-3/5/7` | blur + the above | 12 / 18 / 24 | 4 / 6 / 8 |

The page computes and exports the three RQ2 complexity factors for every cell: the primitive count, the
number of displacement passes, and the filtered area in CSS px² and device px² (diameter² × DPR²).

### Procedure (per run)

1. The page measures the display refresh interval as the median `requestAnimationFrame` interval over 180
   idle frames. You can override it with a fixed Hz value.
2. A grid of config × diameter (100/200/300/400 px) is built. Each **repetition** runs it in a newly
   shuffled order, so thermal drift spreads across all configurations.
3. For each cell, the filter is rebuilt under a new id so no cached filter is reused. The loop then
   waits for the cool-down and starts a rAF loop that moves the loupe every frame.
   * **Path:** a Lissajous path over the whole sandbox, plus seeded random jitter by default. *Random*
     mode teleports the loupe every frame (worst case for caching). The PRNG is seeded, so every
     browser and device sees the same sequence.
   * The first **60 frames are discarded** (shader compilation, texture upload). After that, frames are
     recorded for the configured duration.
4. Per cell the page records p50 / p95 / p99 / max frame interval, mean, SD, and the share of frames
   **over budget** (interval > 1.5 × refresh interval). It also estimates dropped frames as
   Σ(round(interval / refresh) − 1). Percentiles use linear interpolation, the same as numpy and `analyze.py`.
5. The summary pools all repetitions per config × size. A configuration **holds the budget** at a
   diameter if ≤ 5 % of its frames are over budget (that is, p95 within 1.5 × refresh). The threshold is
   configurable. The *largest diameter holding the budget* is the largest tested size for which that
   size and every smaller one hold.
6. A cell is marked **invalid** (struck through, excluded from the summary) if the tab became hidden
   during it.

Raw frame intervals are kept in the JSON export, so distributions can be re-analysed later.

### Running a measurement session

* Use the laptop on mains power. The page shows the battery state where the browser exposes it
  (Chromium only).
* Close other apps and tabs. Keep the window in front and do not touch the mouse while a run is going.
* Fill in the *Device* fields (model, CPU/GPU, OS, display). Browser, version, DPR, GPU string and
  measured refresh rate are recorded automatically.
* Suggested settings: 6 s per cell × 3 repetitions. 10 configs × 4 sizes gives about 15 min per run.
  Use 10 s if you want more samples behind p99.
* Export **JSON** (complete, for `analyze.py`) and optionally **CSV** (one row per cell, environment
  columns included so CSVs from different machines can be concatenated).
* Supplementary profiling: record a few seconds of a run in DevTools → Performance (Chrome) or the
  Firefox Profiler, to see where the time goes (raster / GPU / main thread).

### Technique: `backdrop` vs `portal`

* **backdrop** is the demo's technique: `backdrop-filter: url(#filter)` on the loupe. Only Blink
  renders it.
* **portal** is the technique from `cross-browser-compatible.html`: a copy of the content inside the
  loupe, moved opposite to it, with a normal `filter: url(#filter)`.

For RQ3, run both techniques in Chrome and the portal technique in Firefox and Safari. Firefox accepts
`backdrop-filter: url()` at the CSS level (the *CSS ok* column says "yes") but does not render it.
Performance numbers for a combination are only meaningful where the compatibility check shows the
filter actually renders.

## RQ1: visual comparison

* **Interactive:** choose a background (photo, text on dark, text on light, checkerboard, fine stripes,
  colour spectrum), a preview config and a diameter, then drag on the sandbox.
* **Reproducible screenshots:** static mode renders a single frame with no UI:

  ```
  benchmark.html?static=1&technique=backdrop&config=blur-disp-7&size=200&bg=stripes&x=480&y=320
  ```

  Optional parameters: `blur`, `magnification`, `refraction`, `dispersion`. When the frame is stable
  the page sets `<html data-ready="1">`.
  *Stripes* and *checkerboard* show the aliasing from nearest-neighbour displacement most clearly.
  *Colour spectrum* shows the discrete dispersion bands and the dimming from screen blending.

## RQ3: compatibility matrix

```sh
pip install playwright pillow
python -m playwright install chromium firefox webkit
python tools/compat_screenshots.py --url http://localhost:8000/benchmark.html --out compat-out
```

For every engine × technique × config × background, the script screenshots the sandbox and compares
the pixels inside the loupe circle:

* **not-rendered:** less than 1 % of loupe pixels differ from the same engine's `none` render, so the
  filter had no visible effect.
* **identical:** at most 2 % of pixels differ from Chromium, beyond the difference the two engines
  already show with no filter (font antialiasing, etc.).
* **differs:** renders, but differs visibly. An amplified diff image is written to `compat-out/diffs/`.

Output: `compat-out/compat.csv`, plus a matrix (worst outcome over backgrounds) printed to the console.

Playwright's WebKit is not Safari, and headless browsers may use software rendering. Use the script for
compatibility only, never for performance. For real Safari, open the static URLs listed in the CSV
(`url` column) and take screenshots by hand.

Example output from Chromium 159 / Firefox 159 on Linux, from testing the tooling:

| technique | config | Chromium | Firefox |
|---|---|---|---|
| backdrop | disp, blur-disp-7 | reference | not-rendered |
| portal | disp, blur-disp-7 | reference | differs (visible tile seams, different dispersion fringes) |

## Analysis

```sh
python tools/analyze.py results/*.json --out analysis
```

The script pools runs per *device | browser | technique*. It writes `analysis/summary.csv` (p50 / p95 /
p99 / over-budget % / holds budget for each config × size, with the complexity factors) and
`analysis/max_diameter.csv`. If `matplotlib` is installed, it also writes box plots of frame intervals
per diameter.

## Known caveats to state in the report

* rAF intervals measure the frame cadence the page sees. Compositor-only stalls show up as longer rAF
  intervals in Blink and Gecko, but the rAF timestamp precision is reduced in some browsers (Firefox
  ≈1 ms, more with resist-fingerprinting enabled).
* The displacement maps are 200×200 px. At 300 to 400 px loupes (×DPR) they are upscaled, which costs
  sampling resolution but not the number of filter primitives.
* The benchmark moves the loupe directly with a CSS transform, the same way `setLensPosition` does,
  instead of synthesising text selection events. This keeps the input identical across engines.
* The maps in the benchmark are sized in pixels instead of the demo's `100%`, because percentages did
  not cover loupes larger than about 185 px under `backdrop-filter` in Blink.
